# Phase 31 规则与可靠性加固

## 目标

本阶段处理 Phase 29–30 审查后剩余的四个确认问题：设备/Profile 归属可绕过、重复局面要求等长周期、赛后分析 worker 可能永久退出，以及遥控器确认键可能绕过 UI 禁用状态。

## 实现结果

### 设备与 Profile 归属

对局创建、快照、终局、历史列表、历史详情、自适应档案读取以及旧版自适应重置/锁定接口现在都要求 `deviceId + playerId`。服务端在读取或修改数据前验证二者归属；缺少设备标识返回 422，档案不属于该设备返回 404。

这是一条有意的 API 兼容性边界：0.4 之前省略 `deviceId` 的旧客户端必须升级，不能再通过兼容默认值访问 Profile 数据。

### 重复局面与长将

裁定器现在按“当前局面最近三次出现”确定检查窗口，不再要求两段循环拥有相同长度或相同中间局面。若窗口内只有一方在自己的每一步都将军，则该方因反复长将判负；否则按三次重复判和。新增测试覆盖非等长回路和不足三次不裁定。

当前棋谱只记录每步是否将军，因此本阶段覆盖的是重复局面与单方连续长将。正式竞赛规则中的长捉、允许着法与禁止着法等复杂待判局面需要增加攻击目标、交换收益和逐回合责任数据，属于后续独立规则阶段，不能仅凭现有 `givesCheck` 信息可靠裁定。

### 赛后分析 worker 自恢复

worker 主循环会隔离单次迭代异常；领取任务失败时暂停后重试，分析失败后即使“失败状态”写回数据库再次异常，也不会使后台任务永久死亡。取消信号仍正常向上传播，保证服务停机与重启行为不变。

### 鼠标与遥控器禁用态一致

分析请求进行中会同时阻止鼠标和遥控器重复提交候选/分析操作；自适应功能禁用时，遥控器 OK 不再绕过按钮状态执行重置。输入方式仍共享同一套业务入口。

## 后续规则边界

若目标升级为完整复现正式竞赛裁判规则，应单独设计“待判局面责任分析”模块并建立长捉、长兑、长拦、将帅照面组合及混合循环棋谱测试库。本阶段不对这部分作超出当前数据能力的承诺。
