# Phase 10 天猫魔盒真机测试报告

测试日期：2026-08-18  
测试设备：Tmall MagicBox_M_30_F

## 结论

APK 可以在目标盒子上稳定冷启动并完全离线运行，棋盘、中文字体、鼠标和遥控器操作均已通过真机验证。Web Worker 能正确执行三档 AI，AI 计算期间主界面仍由独立线程负责。

当前最需要在 Phase 11 处理的问题是 AI 超时检查粒度：三档难度在真机上都明显超过配置的时间预算。启动性能和内存处于可用范围；渲染帧样本提示老版本 WebView 上仍有优化空间。

## 冷启动

脚本连续执行三次 `force-stop → am start -W`，只记录实际进入 `com.xiangqitv.app/.MainActivity` 的样本。

| 样本 | TotalTime |
| --- | ---: |
| 第 1 次 | 1822 ms |
| 第 2 次 | 1703 ms |
| 第 3 次 | 1878 ms |
| 平均 | 1801 ms |

盒子的厂商应用商店在 APK 安装后偶尔会异步抢占前台。部署和诊断脚本已经加入前台 Activity 校验与最多三次重试，避免把应用商店的启动时间误记为游戏启动时间。

## 内存与 CPU

| 场景 | Total PSS | 进程 RSS | CPU |
| --- | ---: | ---: | ---: |
| 启动稳定后空闲 | 101814 KB | 174 MB | 0% |
| 困难 AI 搜索后 | 112729 KB | 约 201 MB | 峰值约 270% |

AI 搜索后 Total PSS 增加约 10.7 MB，仍适合 1 GB 目标设备。CPU 百分比采用四核总计口径，270% 表示约 2.7 个核心；高负载集中在 AI 思考阶段，完成后会回落。

## AI 真机结果

三档测试都从相同初始局面开始：玩家执红，右侧车前进一步，等待黑方 AI 完成应手。

| 难度 | 配置预算 | 实际结果 | 搜索节点 |
| --- | ---: | ---: | ---: |
| 简单 | 深度 2 / 350 ms | D2 / 2296 ms | 227 |
| 普通 | 深度 3 / 1100 ms | D2 / 2432 ms | 256 |
| 困难 | 深度 4 / 2800 ms | D2 / 4329 ms | 512 |

根因已经定位：AI 当前每 256 个节点才检查一次截止时间。在旧款 32 位盒子上，单个节点生成全部合法走法的成本较高；简单档甚至在到达第 256 次检查前就完成了深度 2，因此完全没有触发预算中止。

Phase 11 优化目标：缩短截止时间检查间隔，并减少递归搜索中重复的合法走法与将军检测成本。在不改变规则正确性的前提下，优先让三档难度的实际耗时贴近配置预算。

## 渲染

困难 AI 遥控器测试期间，重置后的 Android `gfxinfo` 样本为：

- 14 帧
- 10 帧被系统判定为 janky
- P50：46 ms
- P90：250 ms
- P95：450 ms
- High input latency：0
- Slow UI thread：1

该样本数量很少，并包含 ADB 逐键注入和 WebView 首次状态更新，不能直接等同于连续动画帧率。应用没有持续动画，实际操作和 AI 回合均能完成；Phase 11 仍应复查阴影、渐变和棋盘重绘成本。

## 输入验收

- 鼠标：用户已验证选择、移动、操作按钮正常。
- 遥控器：用户已验证可以完成棋盘与操作区控制；本轮脚本也通过 DPAD/确认键自动完成了模式切换、难度切换和完整 AI 回合。
- 输入模式切换不会重置棋局。

## 复测

连接盒子后执行：

```bash
./scripts/profile-device.sh
```

脚本会采集设备信息、三次有效冷启动、空闲 CPU/内存，并用遥控器键值完成一轮困难 AI 后采集 CPU、内存、渲染和前台 Activity 状态。
