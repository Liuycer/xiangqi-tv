# Phase 30 outbox 同步可靠性

Phase 30 修复客户端离线对局队列的坏数据阻塞问题。旧实现对所有非 2xx 响应采用相同策略：保留队头并停止同步。因此一个永远无法成功的 400、404 或 422 请求会在每次启动和每次新操作时再次失败，后续对局永远没有发送机会。

## 错误分类

队列现在按恢复可能性处理失败：

| 类型 | 处理方式 |
| --- | --- |
| 401、403 | 保留队头；允许更新客户端令牌后恢复 |
| 408、425、429 | 保留队头；等待后续 flush 重试 |
| 5xx、请求超时、网络错误 | 保留队头；等待服务恢复或网络恢复 |
| 其他非成功 HTTP 响应 | 判定为当前请求无法自行恢复，移入隔离区 |

正常成功请求继续按 FIFO 发送；只要队列中还有下一项，两次请求之间仍等待 4.2 秒，避免离线积压抢占历史、Profile 和 AI 的交互请求额度。

## 按对局隔离

永久失败不是只删除一个数组元素。start、snapshot 和 finish 存在依赖关系，如果 start 已被服务器拒绝，继续发送同一局的 snapshot/finish 只会产生更多 404。

客户端因此按 `gameId` 隔离当前所有待传操作：

- 实际被拒绝的请求保存服务器状态码；
- 同一局尚未发送的依赖项标记为 424；
- 隔离记录带 UTC `failedAt`，保存在 `xiangqi-tv-game-outbox-failed-v1`；
- 最多保存最近 30 条诊断记录，避免长期占满 WebView localStorage；
- 隔离完成后继续处理下一局，不影响棋盘交互。

隔离区只用于诊断，不参与正常历史列表，也不会自动重放已经被服务器确定拒绝的数据。

## 验证结果

新增测试覆盖：

- 422 队头和同局依赖项被隔离，下一局仍成功上传；
- 401、403、408、425、429、500、503 均保留队列；
- `Failed to fetch` 网络错误不删除数据；
- 正常多局仍保持 FIFO 和节流。
